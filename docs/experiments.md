# Безопасная лабораторная программа

Цель следующих этапов — проверить открытые гипотезы, не затрагивая реальные адреса, кошельки и публичную сеть.

## Общие требования

- Отдельная offline VM или физически изолированный стенд; сетевые адаптеры выключены.
- Только вновь создаваемые искусственные ключи. Не копировать настоящий `wallet.dat` и не использовать личную passphrase.
- Журналировать return codes, версии, хеши и вызванные API. Не экспортировать приватные скаляры; для snapshot-теста достаточно публичных значений искусственных пар.
- Не заменять системные DLL. Отказы эмулировать в отдельном тестовом процессе через контролируемые hooks/mocks.
- Заранее фиксировать сценарий и критерий результата. Отсутствие повторов не является доказательством криптографической стойкости.

## 1. OpenSSL 0.9.8h: матрица отказов

**Вопрос:** действительно ли ключевой путь останавливается при недостаточной учтённой энтропии и какие API способны изменить результат?

Небольшой 32-bit Windows probe должен загрузить исследуемую `libeay32.dll`, вывести `SSLeay_version`, вызвать `RAND_status`, `EC_KEY_new_by_curve_name(NID_secp256k1)`, `EC_KEY_generate_key`, повторный `RAND_status` и записать ошибки OpenSSL. Каждый сценарий запускается в новом процессе.

Матрица независимых и комбинированных отказов:

- `CryptAcquireContextW` / `CryptGenRandom`;
- `NetStatisticsGet`;
- `CreateToolhelp32Snapshot` и связанные функции;
- `QueryPerformanceCounter`;
- `HKEY_PERFORMANCE_DATA/Global` для Bitcoin-side harness;
- USER32 cursor/queue;
- screen `BitBlt` для service-сценария.

**Подтверждение fail-closed:** при полном отказе источников `RAND_status=0`, генерация возвращает ошибку, новая запись ключа отсутствует. Если генерация успешна, журнал обязан показать, какой другой источник сработал.

## 2. Snapshot/clone: проверка гипотезы повторяемости

**Вопрос:** может ли формальный счётчик энтропии оказаться достаточным при низкой фактической непредсказуемости на клонированной VM?

1. Создать новую offline VM и snapshot до первого запуска probe.
2. Сгенерировать серию искусственных EC-пар; сохранить только публичные значения и return codes.
3. Восстановить snapshot и повторить.
4. Повторить с нормальным CryptoAPI, затем с отказом CryptoAPI при включённых/отключённых NetAPI и Toolhelp.
5. Сравнить публичные значения и журналы входных API.

Повтор публичного значения подтвердил бы повторяемость именно лабораторных ключей. До такого результата сценарий остаётся гипотезой, а не утверждением об исторических кошельках.

## 3. Ранняя Berkeley DB: атомарность записи

В отдельном каталоге с искусственным кошельком проверить:

- успех создаёт `key` и `defaultkey`;
- принудительный `EC_KEY_generate_key=0` не создаёт `key`;
- ошибка Berkeley DB приводит к `AddKey=false` и исключению `GenerateNewKey`;
- повторный запуск читает существующий ключ без новой генерации.

Полный Bitcoin node для этого не нужен; предпочтителен минимальный harness.

## 4. Современный `getentropy`: fault injection

**Вопрос:** подтвердить динамически уже видимую в машинном коде ветку отказа.

В отдельном regtest-процессе перехватить только тестовый вызов `getentropy` и вернуть ошибку. Ожидание: `RandFailure()` и аварийное завершение до выдачи кандидата приватного ключа. Отдельно проверить startup sanity check и создание кошелька.

Это не следует выполнять на процессе с настоящим кошельком: принудительный `abort` может повредить данные.

## 5. SQLite: логические записи и остаточные страницы

Уже подтверждено: зашифрованный при создании кошелёк имеет 8 `walletdescriptorckey`, 0 `walletdescriptorkey`, 1 `mkey`, `integrity_check=ok` и режим `0600` в исследованной среде.

Следующий необязательный этап — криминалистический анализ копии искусственного файла до/после `VACUUM`, включая freelist и незанятые страницы. Наличие или отсутствие логических записей само по себе не доказывает отсутствие следов в slack space.

## Что не входит в программу

- Поиск повторов или слабых ключей среди существующих адресов.
- Подбор приватных ключей, проверка балансов, сканирование публичной цепи или сети.
- Атаки на реальные системы, кошельки третьих лиц и исторические средства.
- Вывод «слабых исторических ключей» из версии OpenSSL, возраста SHA-1 или одной формальной оценки энтропии без воспроизводимого дефекта.
